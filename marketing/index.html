How it works

Seven stages. One report.

Each stage writes a file you can read and correct before the next one runs. Everything stays local until you explicitly pass --remote to a live target.

replay is the heart: the same cases through your recorded baseline and the candidate target, side by side

01

Import

Pull in traces from OTLP, JSONL, Langfuse, or Parquet exports, or read the coding-agent sessions already on disk. Secrets are redacted on the way in.

02

Profile

Surface system prompts, tool schemas inferred from observed calls, provider mix, and error samples. You get an editable app config as a starting point.

03

Map

Group traces into provisional workflows with confidence and uncertainty flags. Correct the labels; re-runs keep your edits.

04

Select cases

One case per representative trace: common, costly, risky, and failed paths. Edit the default checks to define what success actually means.

05

Replay

The same cases through the recorded baseline and the target adapter, checkpointed after every case. Tool proposals are captured, never executed.

06

Compare

Verdicts with written reasons, tool behavior findings, and a guard for checks that fail on both sides. Uncertain is a first-class answer.

07

Report

A local, self-contained HTML and JSON report: verdicts, failure groups, capability gaps, prioritized fixes, usage by provenance.

Four verdicts. No lies.

Every case ends in exactly one of four states, with written reasons you can audit. Unknown checks never silently pass.

pass: checks met fail: check failed error: provider errored uncertain: with reasons
The mis-specification guard: if a check also fails against your recorded baseline, the report suspects the check, not the provider. A broken test never masquerades as a broken switch.
run/report.json · shape of a verdict
"verdict": "uncertain",
"why": [
  "target skipped the recorded tool call",
  "final text still matches the check"
],
"mis_spec_guard": "this check also fails against
 the recorded baseline: fix the check first"
// tool findings: missing / added / argument drift
// usage reported by provenance, never merged

Input: the traces you already have

Zero instrumentation. SwitchIt! reads what your stack and your coding agents already wrote to disk, and applies the same redaction and provenance rules to every source.

Bring your exports

Whatever your observability stack already produces.

  • OpenTelemetry / OTLP JSON, gen_ai conventions
  • JSON and JSONL traces
  • Langfuse-style exports
  • Parquet, or a ZIP of traces.parquet (optional pyarrow extra)

plus an app-config JSON with your prompts and tool definitions, or let the profiler infer one

Or read your coding-agent sessions

Rich agent traces, already on disk, with switchit import --agents.

  • Codex, Claude Code, OpenCode
  • Cursor, Cline, Gemini CLI, Copilot CLI
  • Aider, by explicit path (--aider .aider.chat.history.md)
  • Devin cloud sessions via the official API (explicit opt-in, credentials from the environment)

same redaction, same provenance rules, every source · Windsurf: not yet, no public chat-store format

Output: any provider you might switch to

The line that never moves

SwitchIt! is built to be safe to run on real traces. These rules are enforced in code, not promised in a policy.

  • Secrets are redacted at import. Redacted content is the only content stored, replayed, or reported.
  • Tool calls are captured, never executed. No reads against your live tools, no writes to your data.
  • Offline until you say otherwise. Live targets refuse to run without the explicit --remote flag.
  • Keys come from the environment. Never the command line, never a file, never a tool argument.
  • Usage stays separated. Recorded, estimated, and unknown tokens are reported apart, never merged into one number.
  • Runs are fingerprinted. Changed cases, adapters, or runner code refuse to resume; nothing is silently mixed.
live replay is an explicit opt-in
# without --remote, live targets refuse to run
$ export OPENAI_API_KEY='...'
$ switchit replay --target openai \
    --target-model gpt-4o-mini --remote

The switch problem

“How do people switch from one AI setup to another — Claude Code to Codex to Devin, assistants to APIs — entire env setups at once? It feels like a hassle all the time.”

Local sessions

↗

Claude Code, Codex, Cursor, OpenCode, Cline, Gemini CLI, Copilot CLI already write full traces on disk. Read them with zero instrumentation.

Cloud sessions

↗

Devin comes in through its official API — prompt, status, pull requests — with every session tagged cloud or local. Grok, Groq, vLLM and friends are one-flag replay targets.

Evidence, not vibes

↗

Four verdicts — pass, fail, error, uncertain — with a guard that flags checks even the historical reference fails. Nothing claims readiness it cannot prove.

Any agent can drive it

A built-in MCP server exposes the whole pipeline as ten tools, so Claude Code, Codex, OpenCode, Cursor, or your own agent can run imports, replays, and reports natively instead of shelling out.

The safety model carries over unchanged: everything is offline until the agent explicitly passes remote: true with a live target, and keys still come from the environment. An agent cannot talk a key out of you through a tool argument.

What SwitchIt! will not claim

  • Workflow labels are triage aids, not measured accuracy.
  • Proposed tool calls are captured, never executed.
  • A historical response is reference, not proof of success.
  • Usage is telemetry, not invoices.
  • End-to-end outcomes stay unverified until a safe tool fixture exists.
